## 2. NIP-17 encrypted DMs — remove the app claim

The reviewed app's native DM operation publishes a kind 41010/41011 event to open or extend a relay-backed channel: [src-tauri/src/relay/channel_writes.rs:313](https://github.com/block/buzz-app/blob/c3d2b046a8773824244735750c8d87a23da36218/src-tauri/src/relay/channel_writes.rs#L313). Its normal message sender builds kind 9 events with `content: text(message.content)` and an h/channel tag: [src/features/relay/messages.ts:434](https://github.com/block/buzz-app/blob/c3d2b046a8773824244735750c8d87a23da36218/src/features/relay/messages.ts#L434). The source has no NIP-17 gift-wrap construction/decryption path in the current app native/renderer code searched. This positively traced ordinary path does not establish encrypted native DMs.

The core relay does distinguish and accept gift-wrap events: [crates/buzz-relay/src/handlers/event.rs:744](https://github.com/block/buzz/blob/69ea27343c9b60eeeb1f6e903529cd8b789e910e/crates/buzz-relay/src/handlers/event.rs#L744), [crates/buzz-relay/src/handlers/ingest.rs:2845](https://github.com/block/buzz/blob/69ea27343c9b60eeeb1f6e903529cd8b789e910e/crates/buzz-relay/src/handlers/ingest.rs#L2845). A source test constructs a kind GiftWrap with ciphertext as a literal and asserts recipient-filter admission: [crates/buzz-relay/src/push_runtime.rs:850](https://github.com/block/buzz/blob/69ea27343c9b60eeeb1f6e903529cd8b789e910e/crates/buzz-relay/src/push_runtime.rs#L850). That checks transport authorization, not encryption, decryption or current native DM UX. It cannot justify “Buzz has NIP-17 encrypted DMs” or “both products encrypt chats.”

**Editorial action:** omit Buzz encryption and the parity claim from public copy. Keep the narrower relay observation internally. Do not replace it with a public categorical claim that Buzz has no encryption anywhere.
